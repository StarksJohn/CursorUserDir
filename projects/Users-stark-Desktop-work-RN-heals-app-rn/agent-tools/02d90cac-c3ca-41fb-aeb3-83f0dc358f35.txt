**alex-boards** commented on 2026-06-25T08:48:05Z:

> This still reproduces on the current release (2.6.1) when driving Maestro through the `maestro mcp` server, and I've opened a fix: #3385.
> 
> ### Root cause
> 
> The MCP server caches **one device session per device** (`McpMaestroSessionManager`) and reuses it for every `run` / `inspect_screen` / `take_screenshot`. That session wraps a live connection to the on-device driver (`dev.mobile.maestro`). If the on-device driver dies **out-of-band** while the session is cached — e.g. a second Maestro process (Maestro Studio, another CLI) reinstalls/restarts the shared driver, or the device reboots — the connection goes permanently `DEAD`. The server kept handing back the dead session, so the **first** `launchApp` succeeds and **every** call after the eviction fails (`Unable to launch app`, `inspect_screen` → `UNAVAILABLE`) until the server is manually restarted/reconnected. `maestro test` from the CLI never shows it because it's a fresh process per run; only the long-lived `maestro mcp` server caches across calls.
> 
> ### Reproducer (self-contained, uses the docs' Wikipedia sample app)
> 
> It needs no second Maestro install: it drives the real `maestro mcp` server over stdio JSON-RPC, launches once (establishes the cached session), then simulates the eviction deterministically with `adb uninstall dev.mobile.maestro` — exactly the state a competing Maestro process leaves behind — then launches again.
> 
> - Affected build → 2nd launch fails, exit **1**.
> - Fixed build (#3385) → MCP detects the dead session, rebuilds it (reinstalling the driver), 2nd launch succeeds, exit **0**.
> 
> **Prereqs:** an Android emulator + `adb` on PATH, a `maestro` CLI, and the Wikipedia sample app:
> ```sh
> maestro download-samples
> adb install -r ~/.maestro/samples/apps/wikipedia.apk
> # or: curl -LO https://storage.googleapis.com/mobile.dev/cli_e2e/wikipedia.apk && adb install -r wikipedia.apk
> ```
> 
> **`flow/launch.yaml`**
> ```yaml
> appId: org.wikipedia
> ---
> - launchApp:
> clearState: true
> ```
> 
> **`reproduce.sh`**

> ### Result (same script, two builds)
> 
> ```
> # current main
> >> [1/3] launchApp #1 (cold) ...
> OK: first launch succeeded.
> >> [2/3] simulating eviction: adb uninstall dev.mobile.maestro ...
> >> [3/3] launchApp #2 on the SAME MCP session ...
> server reply: {"id":11,"result":{"content":[{"text":"Failed to run flow: Unable to launch app org.wikipedia","type":"text"}],"isError":true},"jsonrpc":"2.0"}
> BUG REPRODUCED (#2839) # exit 1
> 
> # with #3385
> >> [3/3] launchApp #2 on the SAME MCP session ...
> server reply: {"id":11,"result":{"content":[{"text":"{\"success\":true,\"commands_executed\":2,\"message\":\"Flow executed successfully\"}","type":"text"}],"isError":false},"jsonrpc":"2.0"}
> PASS: 2nd launch SUCCEEDED # exit 0
> ```
> 
> ### Fix (#3385)
> 
> `McpMaestroSessionManager.withSession(...)` now self-heals: if the block throws and the cached session's driver reports `isShutdown()` (connection `DEAD`), it evicts + closes the stale session, rebuilds it (re-running `driver.open()`, which reinstalls the on-device driver) and retries once. Web sessions are skipped from the probe (`CdpWebDriver.isShutdown()` closes the browser as a side effect); a normal flow failure leaves the driver alive and is re-thrown unchanged, so only genuine transport deaths trigger the one-shot rebuild.
