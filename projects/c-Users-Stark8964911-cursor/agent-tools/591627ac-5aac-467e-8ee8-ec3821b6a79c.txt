服务选择策略\n\n可以把 MCP 选择理解成一个简化判断树：\n\n1. 已知路径吗？\n2. 如果已知路径，先用基础文件工具\n3. 如果不知道路径，只是工作区内搜索，先用 `rg` / `Glob`\n4. 如果问题需要“真实外部系统能力”，再考虑 MCP\n5. 如果只是为了省几步点击，不值得专门开 MCP\n\n最实用的经验是：\n\n- **文件问题**：先文件工具\n- **代码搜索问题**：先 `rg` / `Glob`\n- **浏览器问题**：再考虑 `playwright` / `puppeteer`\n- **外部服务问题**：再考虑对应 MCP\n- **最新文档问题**：再考虑 `context7`\n\n### 6.4b 你当前场景下的 MCP 选型建议\n\n| 需求 | 优先方案 | 备注 |\n|------|----------|------|\n| 看本地代码 | `ReadFile` / `rg` / `Glob` | 不需要 MCP |\n| 看最新官方文档 | `context7` 或联网 | 适合版本敏感问题 |\n| 做网页验证 | `playwright` / `puppeteer` | 适合浏览器交互 |\n| 操作 GitHub | GitHub MCP 或 `gh` | 看是否需要真实远程操作 |\n| 查本地 SQLite | SQLite MCP | 适合结构化查询 |\n| 查 npm 包信息 | npm MCP 或官方文档 | 适合依赖核对 |\n\n### 6.4c 哪些 MCP 最容易被滥用\n\n最常见的滥用有三类：\n\n1. 已知文件路径还去走 filesystem 类能力\n2. 只是在仓库里搜文本，却去调用外部能力\n3. 为了“展示工具很多”而不是为了真正提效\n\n避免滥用的关键不是少用工具，而是让每类工具只做自己最擅长的事。\n\n### 6.5 什么时候不值得用 MCP\n\n以下场景优先用基础工具：\n\n- 已知绝对路径读文件\n- 在当前工作区搜索文本\n- 搜索文件名\n- 单文件小改动\n- 轻量文档查看\n\n### 6.6 MCP 变更后的最小回归检查\n\n1. 重启 Cursor\n2. 新开 Chat\n3. 调一次最常用的 MCP 能力\n4. 验证是否仍可正常读取项目文件\n5. 验证 Rules 和命令系统没有受影响\n\n### 6.6a 推荐的 MCP 验证顺序\n\n如果一次改了多个 MCP，不要随机点着试，建议用下面顺序：\n\n1. 先验证最基础、最常用的 MCP\n2. 再验证依赖外部程序的 MCP\n3. 再验证依赖浏览器或系统环境的 MCP\n4. 最后验证低频 MCP\n\n这样做的好处是：一旦基础层就失败，可以更快判断是全局配置问题，而不是某个单独服务问题。\n\n### 6.6b 验证清单\n\n建议最少做下面这些检查：\n\n- MCP 是否在界面中可见\n- 命令是否能正常启动\n- 路径是否存在\n- 返回内容是否符合预期\n- 是否引入新的权限或环境报错\n- 是否影响原本的 Rules / Commands 工作流\n\n### 6.6c 出问题时的排查顺序\n\n当某个 MCP 失效时，建议按这个顺序排查：\n\n1. 看是不是没重启 Cursor\n2. 看路径是不是仍存在\n3. 看命令是不是当前系统可执行\n4. 看依赖程序是否安装\n5. 看是不是该 MCP 本身只支持特定系统\n6. 再考虑是否是配置字段写错\n\n这个顺序的好处是优先排最常见、最便宜的问题。\n\n---\n\n## 不让模型反复重复上下文\n\n### 9.1a 日常策略\n\n把日常使用习惯固定下来，比临时想“怎么省 token”更有效。推荐形成下面这套默认动作：\n\n1. 开始前先写清目标\n2. 只给本轮真正相关的文件\n3. 如果文件很大，先读目录或局部片段\n4. 一轮只解决一个主要问题\n5. 完成一个阶段后及时开新 Chat\n\n这样做的意义在于，你不是在“省一句话的 token”，而是在避免把整个会话结构做重。\n\n### 9.1b 哪些动作几乎一定会让成本上升\n\n下面这些行为通常最容易让成本明显上升：\n\n- 一次塞进多个需求\n- 带大量无关文件\n- 反复上传图片\n- 在同一个 Chat 里跨主题跳转\n- 每轮都重复贴完整背景\n\n它们的共同问题不是“字多”，而是“无关上下文占比过高”。\n\n### 9.2 为什么“少带无关上下文”比“改几个词”更重要\n\n很多人会把注意力放在提示词措辞上，但真正的大头通常是：\n\n- 你给了太多不相关文件\n- 对话历史太长\n- 图片太多\n- 需求混在一起\n- 每轮都重复整段背景\n\n因此更有效的原则是：\n\n- 明确目标\n- 缩小上下文\n- 按任务拆轮次\n- 只读必要文件\n\n### 9.2a 你最应该优先压缩的不是提示词，而是上下文结构\n\n真正影响成本和稳定性的，通常是下面这四件事：\n\n1. 当前轮带了多少文件\n2. 当前 Chat 历史有多长\n3. 本轮任务是否单一\n4. 是否引入了图片或外部长文档\n\n如果这四件事控制住了，提示词本身即使自然表达，通常也不会成为最大问题。\n\n### 9.3 图片为什么成本高\n\n因为图片通常会：\n\n- 引入额外视觉处理成本\n- 迫使模型消耗更高模态预算\n- 让无关信息一起进入上下文\n\n所以你现在这套规则中“能文字就文字，能精确路径就精确路径”的思路是对的。\n\n### 9.3a 高成本场景\n\n下面这些场景最容易出现“单次成本异常高”：\n\n#### 场景 1：长历史 + 新问题\n\n你已经在一个 Chat 里聊了很多轮，又突然切到新主题。  \n此时模型不但要处理新问题，还要背着旧历史一起走。\n\n#### 场景 2：大文件 + 图片 + 多问题\n\n这三者叠加时，成本通常会明显上升，而且输出质量反而可能下降。\n\n#### 场景 3：高价模型做低价值重复工作\n\n例如用 `Opus 4.6` 连续做很多普通改字、低复杂度小修，这种用法通常不划算。\n\n#### 场景 4：反复让模型重新理解同一份背景\n\n如果同一份项目背景已经稳定，最好沉淀到 Rules 或文档，而不是每轮重新贴。\n\n### 9.3b 高成本场景的对应动作\n\n| 高成本场景 | 更优做法 |\n|------------|----------|\n| 长历史 + 新主题 | 开新 Chat |\n| 大文件 + 多问题 | 拆成多轮、分段读取 |\n| 频繁图片输入 | 改为文字描述或精确路径 |\n| 高价模型做低价值任务 | 换成 `Composer 2 Fast`、`Composer 2` 或 `GPT-5.3 Codex` |\n| 重复背景 | 固化到 Rules / 项目上下文 |\n\n### 9.4 适合长期保留的 Token 优化规则\n\n- 先问目标，再给上下文\n- 已知路径直接读\n- 先最小上下文，再必要扩展\n- 每次只做一个主要任务\n- 复杂问题拆成“理解 / 定位 / 实现 / 验证”\n\n### 9.4a 常见误区说明\n\n#### 误区 1：只要提示词更短，就一定更省\n\n不一定。  \n如果你虽然把问题写短了，但仍然带了很长的历史和很多无关文件，成本并不会明显下降。\n\n#### 误区 2：一直在旧 Chat 里追问更高效\n\n不一定。  \n旧 Chat 可能已经把很多无关假设和历史答案也一起带进来了。\n\n#### 误区 3：高价模型一定更划算\n\n不一定。  \n高价模型适合高价值、高复杂度任务；低复杂度日常任务反而更适合 `Composer 2 Fast`、`Composer 2` 或 `GPT-5.3 Codex`。\n\n#### 误区 4：图片比文字更省解释成本\n\n很多时候反而更贵。  \n如果图片本身信息密度低、包含大量无关内容，视觉输入只会增加处理负担。\n\n#### 误区 5：多问几个问题，省得重复开 Chat\n\n这通常是“省步骤，不省成本”。  \n一旦主题变多，模型就需要在同一轮里维持更多分支。\n\n### 9.5 不同模型下的实用节奏\n\n#### `Composer 2 Fast` / `Composer 2`\n\n适合：\n\n- 日常持续迭代\n- 多步工具调用\n- 经常改文件的任务\n\n建议：\n\n- `Composer 2 Fast` 适合日常高频交互\n- `Composer 2` 适合更看重 cost per token 的长会话\n- 两者同智力，主要差别不在解题上限，而在速度和单价\n\n#### `GPT-5.4`\n\n适合：\n\n- 疑难任务\n- 模糊需求\n- 高复杂度实现\n\n建议：\n\n- 明确约束与边界\n- 少让它在无关背景中漫游\n- 让问题聚焦在一个核心难点上\n\n#### `Opus 4.6`\n\n适合：\n\n- 架构评审\n- 安全审查\n- 高价值决策\n\n建议：\n\n- 把它留给“贵但值得”的问题\n- 不要拿它做大量日常重复改动\n\n### 9.6 一个实用的日常节奏模板\n\n你可以把一天中的大多数任务，按下面模板来跑：\n\n1. 先判断任务属于日常改动还是高难问题\n2. 日常改动优先 `Composer 2 Fast`\n3. 高难问题切 `GPT-5.4`\n4. 需要架构评审时切 `Opus 4.6`\n5. 每完成一个阶段就收束并开新 Chat\n\n这个节奏的重点不是“永远固定一个模型”，而是让模型切换有明确目的。\n\n---\n\n## 十、会话管理\n\n### 10.1 新 Chat 什么时候开\n\n建议在下面几种情况开新 Chat：\n\n- 已经问了 3-5 轮\n- 问题主题发生切换\n- 已经完成一个阶段性目标\n- 你开始感觉模型在重复或跑偏\n- 你需要重新压缩上下文\n\n### 10.2 为什么“继续在旧 Chat 问”经常更贵\n\n因为旧 Chat 会携带：\n\n- 历史回答\n- 旧文件上下文\n- 旧决策分支\n- 旧假设\n\n如果你当前问题已经变了，这些历史很容易变成纯成本。\n\n### 10.2a 什么情况下应该继续在旧 Chat 里问\n\n旧 Chat 并不是一律不好。以下场景继续在旧 Chat 里通常更划算：\n\n- 你还在同一个任务链里\n- 之前的决策和上下文仍然直接相关\n- 当前轮是在做上一轮的实现或验证\n- 你需要模型保持同一份局部代码记忆\n\n### 10.2b 什么情况下应该果断开新 Chat\n\n一旦出现下面任一情况，通常就该开新 Chat：\n\n- 主题变了\n- 文件范围变了\n- 你要从实现切到架构讨论\n- 你发现模型开始重复旧假设\n- 你需要更短、更干净的回答\n\n### 10.2c 一个简单判断法\n\n你可以问自己一句话：  \n“如果把前 5 轮都删掉，这一轮还需要它们吗？”\n\n- 如果答案是“基本不需要”，就开新 Chat\n- 如果答案是“必须依赖”，就继续在旧 Chat\n\n### 10.3 一个推荐的轮次结构\n\n复杂任务建议用四步循环：\n\n1. 理解\n2. 定位\n3. 实现\n4. 验证\n\n每完成一轮，如果主题要变，就开新 Chat。\n\n### 10.4 如何减少“模型越来越啰嗦”\n\n可从以下几方面入手：\n\n- 限制一次只处理一个核心问题\n- 不要让历史对话过长\n- 在需求里写清“请简洁回答 / 请先给结论”\n- 对高难但边界清晰的问题优先用 `GPT-5.4`\n\n### 10.4a 一个适合长期使用的会话模板\n\n如果你想让日常会话更稳定，可以采用下面这个结构：\n\n```text\n目标：\n涉及文件：\n约束：\n希望产出：\n如果需要修改文件，请先给最小方案。\n```\n\n这个模板的价值在于：\n\n- 强制问题聚焦\n- 减少无关展开\n- 让模型更快进入可执行状态\n\n### 10.4b 会话管理的核心不是“更短”，而是“更干净”\n\n很多时候模型变啰嗦，不是因为你没写“请简洁回答”，而是因为：\n\n- 上下文太脏\n- 主题太混\n- 任务边界不清\n- 历史轮次太长\n\n因此会话管理的核心目标不是机械缩字数，而是提高“相关信息占比”。\n\n---\n\n## 十一、Skills
