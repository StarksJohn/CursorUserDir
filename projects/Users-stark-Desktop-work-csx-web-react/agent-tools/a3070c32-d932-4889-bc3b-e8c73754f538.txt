> The root cause of this Codex CLI bug isn’t just “one thing” — it’s a combination of authentication and environment misalignment introduced in the 0.41–0.43 branch. 
> Here’s a clear technical breakdown 👇 
> 
> 🔍 Root Cause Summary 
> 
> 
> Codex CLI ( codex-cli 0.43.x) uses multiple authentication and networking backends — ChatGPT SSO, OpenAI API key, and OpenRouter routing. 
> When these collide or get misdetected, the CLI sends requests to the wrong API endpoint or with invalid tokens, leading to: 
> 
> 401 Unauthorized errors 
> 
> Broken SSE (Server-Sent Events) streams in TUI mode 
> 
> Sudden disconnects when using models like gpt-5-codex 
> 
> 
> ⚙️ Detailed Breakdown 
> 
> 
> 1.   SSO Token Mismatch 
> 
> The “Sign in with ChatGPT” SSO flow issues a short-lived JWT token, valid only for ChatGPT web context. 
> 
> Codex CLI, however, sometimes tries to reuse it for OpenAI’s API endpoints (api.openai.com/v1/responses) — which reject it with 401 Unauthorized. 
> 
> This happens because CLI doesn’t refresh the SSO token correctly or misidentifies the provider. 
> 
> 
> 
> Symptoms: 
> 
> /status shows “Logged in with ChatGPT” but every call to OpenAI fails. 
> 
> codex.api_request lines in logs return 401 even though login appears successful. 
> 
> 
> 2.   Conflicting Environment Variables 
> 
> 
> Many users have legacy or hidden exports like: 
> 
> ```
> OPENAI_API_KEY
> OPENAI_BASE_URL
> OPENROUTER_API_KEY
> API_BASE
> BASE_URL
> ```
> 
> If any of these are set, Codex overrides its SSO provider logic and starts routing via: 
> 
> openrouter.ai (proxy endpoint) 
> 
> or a stale custom OPENAI_BASE_URL 
> 
> 
> 
> Result: 
> SSO token is valid, but requests go to the wrong host → instant disconnection or 401. 
> 
> 3.   Model Access Policy Change 
> 
> gpt-5-codex sometimes requires org-level verification. 
> 
> Normal gpt-5 is public for Plus/Pro/Team SSO users. 
> 
> So the same token can succeed with gpt-5, but fail with gpt-5-codex. 
> 
> 
> 
> This causes false reports of “streaming broken,” while the real issue is permission denial on that specific model. 
> 
> 4.   TUI Stream (SSE) Regression 
> 
> 
> Versions 0.41–0.42 had partial regressions in the SSE handler: 
> the event parser and connection timeout were not robust to partial chunked responses. 
> So even when the model response was valid, the client aborted early. 
> 
> 
> That’s why: 
> 
> codex exec "Say 'pong'" (headless mode) works perfectly, 
> 
> but codex (interactive TUI) drops mid-stream. 
> 
> 
> 5.   Network Layer / SSL Inspection 
> 
> 
> When all else is correct, some macOS setups still interrupt streaming: 
> 
> HTTPS interception (AdGuard, Little Snitch, antiviruses) 
> 
> Corporate proxy rewriting chunked transfer encoding 
> 
> Broken SSE keep-alive frames 
> 
> 
> 
> You can confirm by: 
> 
> ```
> curl -N https://stream.wikimedia.org/v2/stream/recentchange
> ```
> 
> If that stream also dies → it’s the network layer, not Codex. 
> 
> 🧩 So in short 
> 
> | Category | Root Cause | Fix |
> | --- | --- | --- |
> | Auth | ChatGPT SSO token used on API endpoint | Full relogin + remove stale auth.json |
> | Routing | Wrong base URL (OpenRouter / proxy) | Clear env vars & config |
> | Model | Restricted gpt-5-codex | Temporarily use gpt-5 |
> | Client | SSE parser bug in TUI | Use codex exec (headless) |
> | Network | Proxy / SSL inspection | Test SSE with curl; disable filters |
