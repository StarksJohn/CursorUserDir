 # csx-web-react 工程规则信息说明,通用项目配置、环境规则、构建发布流程和验证方式
 
 `csx-web-react` 是独立的 CSX React / Next.js 前端仓库，用于承接 CSX Web 的 React 页面实现。项目拥有独立依赖、构建、测试、CI/CD、发布和回滚边界。
 
 ## 技术栈
 
 - Node `>=20.9`
 - pnpm `>=8.15`
 - Next.js `16.1.1`
 - React / React DOM `19.2.3`
 - TypeScript 5
 - Tailwind CSS 4
 - ESLint 9
 - Playwright
 - Lucide React、qrcode.react、clsx、class-variance-authority、tailwind-merge
 
 项目使用 Next.js App Router 和 static export。只引入本项目需要的前端依赖。

 ## Static Export
 `next.config.ts` 固定使用：
 - `output: "export"`
 - 默认 `basePath=/display-screen-config`
 - 默认 `assetPrefix=/display-screen-config`
 - `trailingSlash=true`
 - `images.unoptimized=true`
 可通过 `NEXT_PUBLIC_CSX_APP_BASE_PATH` 覆盖 `basePath` / `assetPrefix`。正式发布默认使用 `/display-screen-config`。
+当前不直接更改默认 `basePath`，因为旧 `csx` POC / Prod 和 `csx-k8` dev / Prod 已按 `/display-screen-config/**` 部署公开大屏静态产物。若后续项目从显示屏配置扩展为完整平替 `csx-web`，应在独立迁移方案中统一调整挂载前缀、静态目录、pipeline、S3 / CloudFront 或旧 CSX package 映射。
 旧 `csx` artifact 和 `csx-k8` 静态托管都应把 `out/` 内容放到最终站点的 `display-screen-config/` 物理目录下，因此浏览器入口保持：
 ```text
 /display-screen-config/tvScreenNew/?clinicCode={clinicCode}
 ```
 
+### 暂不建议把根挂载前缀改为 `csx-new`
+`csx-web-react` 的仓库名可以承接未来更多 React 页面，但当前默认 `basePath=/display-screen-config` 已进入旧 `csx` POC / Prod 和 `csx-k8` dev / Prod 的部署链路。短期内不建议把根挂载前缀改为 `/csx-new`，原因是这不是单纯的前端路由重命名，而是会改变静态资源、页面入口和部署目录。
+
+如果改为 `/csx-new`，至少会影响：
+- `next.config.ts` 的默认 `basePath` / `assetPrefix`，以及所有 HTML、JS、CSS、图片等静态资源 URL。
+- 公开大屏已有入口，例如 `/display-screen-config/tvScreenNew/?clinicCode={clinicCode}`，现有浏览器书签、设备配置、二维码链接、排障文档和已交付环境都需要同步迁移。
+- 旧 `csx` POC / Prod artifact 的 zip 顶层目录、后端下载校验规则、解压目标目录、CSX package 注入路径和后端静态文件映射。
+- `csx-k8` dev / Prod 的 S3 sync 目标路径、CloudFront invalidation 路径、reverse proxy / domain alias 路径和上线后回滚口径。
+- README、Pipeline、运维部署文档、旧 CSX package release 流程和验收 URL。
+
+如果只是把已部署入口外层加一段 `/csx-new`，例如：
+```text
+https://csx-poc.clinicsolution.hk/display-screen-config/tvScreenNew/?clinicCode={clinicCode}
+-> https://csx-poc.clinicsolution.hk/csx-new/display-screen-config/tvScreenNew/?clinicCode={clinicCode}
+
+https://poc.demo.clinicsolution.hk/display-screen-config/tvScreenNew/?clinicCode={clinicCode}
+-> https://poc.demo.clinicsolution.hk/csx-new/display-screen-config/tvScreenNew/?clinicCode={clinicCode}
+```
+影响仍然不是单纯改入口文案：
+- 前端 static export 需要先选定真实运行策略：要么把 `basePath` / `assetPrefix` 改为 `/csx-new/display-screen-config` 并重新构建所有环境产物；要么继续构建 `/display-screen-config`，由服务器把 `/csx-new/display-screen-config/**` rewrite 到旧目录。两种策略不能混用，否则 HTML 入口、`_next` chunk、字体、图片和 `public/display/**` 资源路径会不一致。
+- 对 `csx-k8` dev / POC：当前 pipeline 把 `out/` 同步到 `s3://${DISPLAY_SCREEN_S3_BUCKET}/display-screen-config/`，并只 invalidation `/display-screen-config/*`。如果入口改为 `/csx-new/display-screen-config/**`，需要同步调整 S3 目录、CloudFront invalidation、reverse proxy / domain routing 和 deep link 配置；否则新 URL 可能 HTML、JS、CSS 或图片 404。
+- 对旧 `csx` POC：当前 React artifact 顶层目录约定是 `display-screen-config/**`，后端 / release owner 的 zip 校验、解压目录、CSX package 注入路径和后端静态文件映射也按这个目录做。如果入口改为 `/csx-new/display-screen-config/**`，需要把 artifact 顶层目录、校验规则、package 注入路径和 IIS / 后端静态映射一起调整，或额外提供 rewrite / redirect。
+- 对既有已部署页面：已发给诊所或设备端的旧 URL、浏览器书签、排障文档和 QA 用例仍会指向 `/display-screen-config/**`。如果不保留旧路径、双目录发布或提供明确 redirect，现有大屏设备和已交付验收入口会中断。
+- 对 API：API host 和 `clinicCode` query 本身不需要因为路径前缀变化而改；旧 `csx` POC 仍应请求同源 `/api`，`csx-k8` dev / POC 仍应请求 `https://api-poc.clinicsolution.hk/api`。但改路径后必须重新验证页面刷新 deep link、静态资源、同源 `/api` 或 K8 API 请求、CloudFront / IIS 缓存和回滚路径。
+
+因此，当前推荐保持 `/display-screen-config` 作为既有部署挂载前缀，在其下新增业务模块路由，例如 `/display-screen-config/management-settings/program-settings/display-screen-config/`。如果后续确认当前项目要完整平替 `csx-web` 并统一使用 `/csx-new`，应作为独立迁移任务处理：先确定新旧路径并行期、兼容重定向或双目录发布策略，再同步前端、后端 release owner、运维和 QA 的验证清单。

 #### 旧 `csx` Prod 部署职责分工
 前端项目配置：
 - `package.json` 中 `pnpm run build:prd` 固定使用 `NEXT_PUBLIC_CSX_SYSTEM=csx` 和 `NEXT_PUBLIC_CSX_ENV=prod`，旧 `csx` Prod artifact 默认请求部署站点同源 `/api`，不写死单一租户域名。
 - `next.config.ts` 使用 static export，默认 `basePath` / `assetPrefix` 为 `/display-screen-config`，构建产物为 `out/`。
 - 旧 `csx` Prod 页面入口按租户域名访问，例如 `https://sfsc3051.clinicsolution.hk/display-screen-config/tvScreenNew/?clinicCode=SFSC`。
 - 本地可用 `pnpm dev:csx:prod` 走旧 `csx` Prod 口径做前端开发验证；正式 artifact 使用 `pnpm run build:prd` 生成。
 - 前端不在旧 `csx-web` 仓库内混入 React 源码，不在 29 / Windows Jenkins 上安装 Node / pnpm 来 build React。
 
 Bitbucket 仓库配置：
 - Run Pipeline 时 Branch 固定选择 `main`。
 - Prod artifact 发布选择 `custom: build-old-csx-prod-artifact`。
 - `Build csx-web-react for old csx Prod` 包括 `pnpm install --frozen-lockfile`、`pnpm run lint`、`pnpm run typecheck` 和 `pnpm run build:prd`。
 - 构建完成后把 `out/` 内容复制到 `react-artifact/display-screen-config/`，再压缩为 `react-artifact.zip`；zip 顶层应只有 `display-screen-config/**`。
 - Bitbucket Downloads 会保留固定 latest 文件 `csx-web-react-old-csx-prod-main-latest.zip`，并同时上传版本化文件 `csx-web-react-old-csx-prod-main-{buildNumber}-{commit}.zip`。
 - Bitbucket repository variables 只维护 `ATLASSIAN_ACCOUNT_EMAIL` 和 `ATLASSIAN_API_TOKEN` 这类上传 Downloads 所需 secret；密钥只放 Bitbucket / Jenkins secret，不写入仓库。
 
 后端 / release owner 配置：
 - 旧 `csx` 最终 release package 仍按原 CSX 打包流程生成；React 项目只提供 `display-screen-config/**` 前端静态 artifact。
 - 旧打包 job 继续维护 `CsxMainVersion`、`CsxEnvironmentName`、`CsxApiBranch`、`CsxWebBranch`、`CsxToolBranch` 等原有参数；Production packaging 的 `CsxEnvironmentName` 使用 `Production`。
 - Jenkins / wrapper 用 Basic auth 从 Bitbucket Downloads 下载 `csx-web-react-old-csx-prod-main-latest.zip` 或同一次构建的版本化 zip。
 - 下载后先按 zip 可打开和必需 entries 校验：必须存在 `display-screen-config/tvScreenNew/index.html`、`display-screen-config/_next/**`、`display-screen-config/display/**`，且 zip 根目录不能有 `index.html`、`weboffice.html` 或 `static/**`。
 - 校验通过后把 `display-screen-config/**` 注入最终 CSX package 的 Web root；同一份 old Prod artifact 进入不同租户最终 package 后会请求各自 host 的同源 `/api`。
 - 后端应用层需保证 `/display-screen-config/tvScreenNew/` 作为 default document / static path 可访问；正式入口不应要求用户访问带 `index.html` 的排障 URL。
 - 旧打包文档中的 package 分发流程仍适用：最终 package 生成后，从 29 服务器 `D:\CsxRelease\release` 取 zip，上传到 `csx-upgrade-package` S3 bucket，并在 CSX&CSM 群通知版本号、环境、任务号、package URL、额外配置和需要单独执行的 SQL。
 - `csx-upgrade-package` S3 bucket 是最终 package 分发位置，不是当前 React static export 的运行时托管位置。
 
 运维配置：
 - 运维继续部署后端 / release owner 生成并分发的最终 CSX package，不单独 build 当前 React 项目。
 - 维护旧 `csx` Prod 各租户域名的既有部署和访问路径，确保 `/display-screen-config/**` 静态资源、`/display-screen-config/tvScreenNew/` deep link 和 query string 可正常访问。
 - 旧 Prod 已验证不需要为当前 React artifact 额外配置独立 S3 / CloudFront，也不需要把入口改成带 `index.html` 的 URL。
 
 旧 `csx` Prod 发布流程：
 1. 前端代码合入远端 `main`。
 2. 在 Bitbucket Pipelines 页面 Run Pipeline，Branch 选择 `main`，Pipeline 选择 `custom: build-old-csx-prod-artifact`。
 3. Pipeline 成功后确认 fixed latest 文件和版本化文件来自同一次最新成功构建。
 4. 后端 / release owner 下载 Bitbucket Downloads zip，校验并注入最终 CSX release package。
 5. 运维按旧 CSX package 流程部署最终 package。
 6. 部署完成后按目标租户验证 `https://{tenant-host}/display-screen-config/tvScreenNew/?clinicCode={clinicCode}`，例如 `https://sfsc3051.clinicsolution.hk/display-screen-config/tvScreenNew/?clinicCode=SFSC`。
