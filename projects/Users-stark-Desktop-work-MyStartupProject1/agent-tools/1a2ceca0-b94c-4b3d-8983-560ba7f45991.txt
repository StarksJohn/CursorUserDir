**nonacc** commented on 2025-11-20T17:45:26Z:

> ### Fix for Prisma 7 Seeding Error (Cannot read properties of undefined (__internal))
> 
> I ran into this issue when trying to seed my PostgreSQL database after upgrading to Prisma v7.
> The error looked like this:
> 
> `TypeError: Cannot read properties of undefined (reading '__internal')
> at new t (.../getPrismaClient.ts:239:27)`
> 
> After some digging, the root cause was that Prisma 7 no longer auto-detects the database provider and now requires an explicit adapter. My previous seeding setup didn't load a provider at all, which resulted in the internal client failing during initialization.
> 
> ### ✅ What fixed it
> 
> Here’s the full list of changes that solved the problem:
> 
> 1. Updated `prisma.config.ts` to use `process.env.DATABASE_URL` (Prisma 7 is strict about where the connection URL comes from.
> 2. Updated the seed script to use `ts-node` instead of `ts-node-dev`; ts-node-dev caused the adapter instance to initialize incorrectly during hot reload.
> 3. Installed the PostgreSQL adapter dependencies: `npm install @prisma/adapter-pg pg`.
> 4. Updated the seed file `(src/prisma/seed/root.ts)` to explicitly use the Prisma 7 PostgreSQL adapter, like so:
> 
> ```
> import { PrismaClient } from '@prisma/client'
> import { PrismaPg } from '@prisma/adapter-pg'
> import { Pool } from 'pg'
> 
> // Set up PostgreSQL adapter for Prisma 7
> const pool = new Pool({ connectionString: process.env.DATABASE_URL })
> const adapter = new PrismaPg(pool)
> const prisma = new PrismaClient({ adapter })
> 
> export default prisma
> ```
> 
> ### Takeaway
> 
> If you're seeding with Prisma 7 + PostgreSQL, you MUST explicitly provide an adapter.. 
> Prisma won’t connect automatically anymore. Once the adapter is wired up, everything works smoothly.
> 
> Hope this saves someone else a couple hours of debugging.

**cleverlight** commented on 2025-11-26T16:22:01Z:

> For me the most difficult breaking change to debug was the difference of the implicit defaults, since Prisma switched to adapters.
> 
> On `6.19` I could use a simple connection string and still be compliant with the "Enforce SSL on incoming connections" in Supabase. When I moved to `7.0.0` I started getting a P1010 error from Prisma ("User {database_user} was denied access on the database {database_name}"). I believe that was misleading, because the error was actually that it couldn't make an SSL connection. Many hours later I arrived at:
> 
> ```javascript
> import {PrismaClient} from "@/../prisma/generated/client";
> import { PrismaPg } from '@prisma/adapter-pg';
> import pg from "pg";
> 
> const config_object = {
> connectionString: process.env.POSTGRES_DATABASE_URL,
> ssl: {
> require: true,
> // even though dotenv can handle new lines in environment variables, not all environments do
> ca: process.env.POSTGRES_SUPABASE_ROOT_CERT?.replace(/\\n/g, '\n') || undefined,
> }
> };
> const pool = new pg.Pool(config_object);
> const adapter = new PrismaPg(pool);
> const prisma = new PrismaClient({ adapter });
> export default prisma;
> ```
> 
> The solution was to add the `ssl` block to the configuration object (which can be used with either `pg.Pool()` or `PrismaPg()` if not connection pooling.
> 
> ```
> const config_object = {
> ...
> ssl: {
> require: true,
> }
> };
> ```
> 
> Once that was there, I started getting a more indicative self-signed cert error, which then led me to properly embed the Supabase root certificate. I hope this breadcrumb trail helps someone else.

**Mauroariza** commented on 2025-11-28T02:20:10Z:

> > @Mauroariza, but what does "prisma/config" points to? 
> 
> Hi! The `"prisma/config"` import refers to the `@prisma/config` package (version 7.0.1), which is an internal Prisma module that provides programmatic configuration APIs for Prisma 7.x. It exports `defineConfig` for structured config and `env` for typed environment variables.
> 
> To get access to `"prisma/config"`, you just need to install Prisma 7.x - it comes bundled automatically. In your `package.json`, add:
> 
> json
> "prisma": "^7.0.1"
> 
> 
> Then run `npm install`. The `@prisma/config` package will be installed as a dependency.
> 
> Here's the folder structure from my project:
> 
> 
> prisma/
> ├── schema.prisma # Main schema with generator + datasource
> ├── prisma.config.ts # Programmatic config using defineConfig
> ├── shared/ # Shared models (users, roles, enums)
> ├── auth/ # Auth models (OAuth, refresh tokens) 
> ├── admin/ # Admin-specific models
> ├── client/ # Client-specific models
> 
> └── migrations/ # Database migrations
> 
> 
> The `prisma.config.ts` file uses it like this:
> 
> typescript

> 
> ```json
> {
> "glob": "generated/**/*",
> "input": "prisma",
> "output": "prisma"
> },
> ```
> 
> Change `node_modules` permissions:
>

**otsairaze** commented on 2025-12-23T00:14:48Z:

> Fixed: "The datasource property is required in your Prisma config file" when using Prisma 7 in Docker
> 
> Hi everyone,
> 
> I spent 3 days troubleshooting an issue with Prisma 7 in a Dockerized environment (NestJS). I kept getting the following error during prisma migrate deploy:
> 
> Error: The datasource property is required in your Prisma config file when using prisma migrate deploy.
> 
> Even though I had the datasource block in my schema.prisma, the migration kept failing. It turns out that in Prisma 7, the prisma.config.ts file is mandatory for runtime operations like migrations in Docker, but it often gets lost during multi-stage builds.
> 
> The Solution: The fix was simple but not obvious: you must explicitly copy the prisma.config.ts file into your final Docker stage.
> 
> Here is the part of my Dockerfile that solved it:
> 
> ```
> COPY --from=builder --chown=node:node /app/prisma.config.ts ./
> ```
> 
> Also, make sure to copy your generated folder or run prisma generate during the build stage to avoid runtime import issues.
