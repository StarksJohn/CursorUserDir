## 五、会话与上下文管理

### 5.1 新 Chat 行为（类似 Claude Code `/clear`）

- 点击 `+` 或 `Ctrl+Shift+N` 开启新 Chat
- 新 Chat 不继承历史对话和之前的文件上下文
- 仍会加载：当前打开文件、工作区、Git 状态、`.cursorrules`

### 5.2 压缩上下文（类似 `/compact`）

Cursor 无 `/compact`，可用：

1. **新 Chat**：每 3–5 轮对话开新 Chat
2. **减少自动加载**：在 `settings.json` 中设置  
   `"cursor.ai.includeOpenFiles": false`,  
   `"cursor.ai.includeRecentlyEditedFiles": false`
3. **精准引用**：用 `@文件路径` 指定文件，避免大范围读取

### 5.3 上下文倍数 (1x / 2x / 4x)

- **1x**：日常编码（推荐）
- **2x / 4x**：长对话、多文件重构时使用，注意 token 增加

## 六、Token 优化策略

### 6.1 每日检查

- 清空前一天对话
- 使用 Sonnet 4.6（非 Opus）
- 上下文倍数 1x
- 简单代码用 Tab 补全，少用 Chat
- 使用 `@` 精准引用
- 每 3–5 轮开新 Chat
- 避免读取图片和大文件
- 用 Grep/Glob 代替全文件 Read

### 6.2 工具使用优先级

| 优先级 | 工具 | 说明 |
|--------|------|------|
| 高 | Tab 补全 | 成本最低 |
| 高 | Grep / Glob | 精确搜索 |
| 中 | Read（带 offset/limit） | 部分读取 |
| 中 | MCP | 按需使用 |
| 低 | 读取整大文件 / 图片 | 尽量避免 |

### 6.3 模型与成本参考（Sonnet 4.6）

| 场景 | 模型 | 估算成本/次 |
|------|------|-------------|
| 简单问答 | Sonnet 4.6 | $0.02–0.05 |
| 代码重构 | Sonnet 4.6 | $0.05–0.12 |
| 复杂分析 | Sonnet 4.6 (Thinking) | $0.10–0.20 |
| 架构设计 | Opus (Thinking) | $0.40–0.60 |

### 5.1 新 Chat 行为（类似 Claude Code `/clear`）

每次点击 `+` 号是**新的独立会话**，类似 Claude Code 的 `/clear`：
- 不会加载历史对话的对话内容
- 不会加载之前读取的文件内容
- 不会加载之前的工具调用结果

**New Chat 的上下文包含**：
- **会自动加载**：当前打开的文件、最近编辑的文件（若 settings 中启用）、工作区路径、Git 状态、`.cursorrules`、`settings.json`、当前光标位置和选中代码
- **不会加载**：之前 Chat 的对话历史、之前读取的文件、工具调用结果、错误信息

### 5.2 关于「清理 Chat 历史」的误解

- **不需要**频繁删除历史 Chat（历史 Chat 不会影响新 Chat 的上下文）
- **应该**每 3–5 轮对话后开启新 Chat（避免当前 Chat 的上下文累积）
- 每周或每月清理一次历史 Chat 即可（保持工作区整洁）

**Token 消耗的真正原因**：
```
单个 Chat 的 token 消耗 = 初始上下文 + 每轮对话 + 累积的对话历史
第 1 轮: 2k + 2k = 4k tokens
第 2 轮: 2k + 2k + 4k(历史) = 8k tokens
第 3 轮: 2k + 2k + 8k(历史) = 12k tokens
第 5 轮: 2k + 2k + 20k(历史) = 24k tokens
第 10 轮: 2k + 2k + 50k(历史) = 54k tokens ← 非常昂贵!
解决方案: 第 3–5 轮后开启新 Chat，重置为 4k tokens
```

**不要**：`请读取 .cursorrules 文件`、`请读取所有配置文件`、`请分析这个目录下的所有文件`  
**应做**：`请用 Grep 搜索 .cursorrules 中的 "MCP"`、`请只读取 @.cursorrules 的第 1–50 行`、`请用 Glob 查找 *.tsx 文件`

### 6.9 MCP 使用指南（来自 TOKEN_OPTIMIZATION_QUICK_REFERENCE）

- **推荐**：context7（技术文档）、chrome-devtools（浏览器调试）、sequential-thinking（深度分析）
- **谨慎**：filesystem（避免列出大量文件）、git（避免完整历史）、sqlite（避免大查询）
- **示例**：`请使用 context7 查询 React Native 最新文档` ✅；`请使用 filesystem MCP 列出 D:\work 下所有文件` ❌

| 读取 1 张图片 | 5,000–20,000 | $0.015–0.06 |

### 6.11 常见错误及处理（来自 TOKEN_OPTIMIZATION_QUICK_REFERENCE）

**错误 1 - 对话成本过高**（单次超过 $0.20）：原因多为长对话、图片、多文件。处理：立即开新 Chat、避免图片、用 Grep/Glob。

**错误 2 - 上下文不足**：原因多为倍数过低或轮数太多。处理：提高倍数（1x→2x）、在提示中重述关键信息、用 @ 引用文件。

**错误 3 - 响应慢**：原因多为上下文过大、大文件、Opus。处理：开新 Chat、运行 `optimize_cursor_token.ps1`、改用 Sonnet。

1. 立即停止当前对话  
2. 点击 New Chat 开新对话  
3. 检查模型（改用 Sonnet 4.6）

## 关于「达到与 Claude Code 相同上下文效果」

需要说明一个本质区别：

**`.cursorrules` 是提示词指令，不是上下文控制机制。** 它告诉模型「应该怎么做」，而不能控制 Cursor 的底层上下文窗口行为。

两者真正的差异在于：

| 机制 | Claude Code | Cursor IDE |
|------|-------------|------------|
| `/compact` 压缩上下文 | 原生支持 | 无，只能开新 Chat |
| `/clear` 清空上下文 | 原生支持 | 开新 Chat（`Ctrl+Shift+N`） |
| `/cost` 查看消耗 | 原生支持 | Cursor 用量页面查看 |
| 上下文内容 | 完全可控 | 自动加载打开文件、git 状态等 |
| 规则加载 | `CLAUDE.md` 自动读取 | `.cursorrules` 自动加载 |

**结论：`.cursorrules` 内容已完整对齐 `CLAUDE.md`，模型行为规范上等价。** 上下文管理的操作方式在 Cursor 中需用「开新 Chat」替代 `/compact` 和 `/clear`，这不是规则文件能解决的，属于 Cursor 产品层面的限制。
