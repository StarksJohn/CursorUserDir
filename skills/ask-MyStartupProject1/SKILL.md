# ask-MyStartupProject1

## 作用
本技能是 `D:/work/MyStartupProject1` 的默认总控入口。

它的职责不是只回答某个点状问题，而是用 BMAD 帮用户完整推进一个项目生命周期：
- 从 `找方向` 到 `是否立项`
- 从 `Product Brief / MVP` 到 `架构与实施准备`
- 从 `开发 / 自动测试` 到 `发布上线`
- 从 `上线后复盘` 到 `后续版本迭代`

## 何时使用
在以下场景默认优先使用本技能：
- 新 chat 里用 `/ask-MyStartupProject1` 恢复项目上下文
- 用户问 `这个方向值不值得做`
- 用户问 `下一步该用哪个 BMAD 角色`
- 用户要推进 `竞品分析`、`Product Brief`、`MVP`、`路线图`、`架构`、`开发`、`测试`、`上线` 或 `迭代`

激活后，默认先恢复本技能中的稳定背景、历史判断和项目文档，再判断当前处于哪个阶段、下一步该走哪个 BMAD 工作流。

## 核心原则
- 先判断 `做不做`，再讨论 `怎么做`
- 先验证 `需求与差异化`，再进入 `Product Brief`
- 先通过 `implementation readiness`，再进入开发
- 先通过 `自动测试 / 回归验证`，再进入上线
- 任一阶段如果关键前提被推翻，优先 `自动回退`，而不是强行往下推进

## 稳定背景
除非用户明确修改，否则默认以下背景：
- 用户为居住在中国大陆且没有公司的独立开发者，前端经验丰富，覆盖 React、React Native、Vue 2、Vue 3、TypeScript、JavaScript、HTML、CSS、小程序、Flutter、iOS、Android
- 希望产品能同时获得美元与人民币收入
- 偏好前期成本低、建设周期短、需求面大、留存扎实、付费转化健康，并具备被动收入潜力
- 当前阶段多为调研、想法验证、产品定义与规划，而非立即写代码
- 默认回复语言为简体中文
- 涉及代码时，代码注释保持英文

- 回退优先于继续推进；不要为了保持流程向前而忽略新的反例、风险或否定信号

## 生命周期状态机
这是本项目默认采用的 BMAD 生命周期状态机；除非用户明确要求跳步，否则按这个顺序推进。
这一版特别强调 3 个常被忽略但必须存在的阶段：
- `问题 / 需求验证`：避免只看市场和竞品，不验证用户是否真的痛
- `立项决策（go / no-go）`：避免分析很多后，没有明确“继续还是停止”
- `增长与迭代决策`：避免上线后只做复盘，不把数据反馈回下一轮产品决策

1. `方向筛选`
- 使用 `bmad-agent-analyst`
- 目标：先筛掉低频、弱付费、强渠道依赖的方向
- 产出：`候选方向清单 + 排除理由`

2. `问题 / 需求验证`
- 使用 `bmad-agent-analyst`、必要时配合 `bmad-domain-research`
- 目标：确认用户是否真的痛、痛点是否高频、是否存在立即付费触发点
- 产出：`问题定义 + 需求验证判断 + 是否继续`

3. `市场与竞品`
- 使用 `bmad-market-research`
- 必做：`中国大陆市场竞品分析 + 海外市场竞品分析`
- 目标：判断市场是否拥挤、价格带、是否存在明显差异化空间
- 判定规则：若 `中国大陆市场` 或 `海外市场` 任意一侧已经得出 `不值得继续`、`过于拥挤且无差异化`、`付费/获客结构不成立` 等否定性结论，则本阶段直接判为 `不通过`
- 回退动作：本阶段一旦 `不通过`，必须回退到上个阶段 `问题 / 需求验证`，重新审视目标用户、痛点强度、付费触发点与方向假设
- 产出：`竞品表 + 差异化判断 + 是否继续`

4. `问题定义与价值主张`
- 使用 `bmad-agent-analyst`
- 目标：明确目标用户、核心痛点、付费时机、用户为何现在就买
- 产出：`目标用户定义 + 核心价值 + 购买触发点`

5. `立项决策（go / no-go）`
- 使用 `bmad-agent-analyst`，必要时配合 `bmad-market-research`
- 目标：基于需求验证、竞品和价值主张，明确 `继续 / 暂停 / 排除`
- 产出：`立项判断 + 核心依据 + 风险清单`

6. `Product Brief`
- 使用 `bmad-product-brief`
- 进入条件：前 5 步已完成，且判断 `值得继续`
- 产出：`产品 Brief`

7. `路线图与 MVP`
- 使用 `bmad-agent-pm`
- 目标：把 Brief 收敛成 MVP 边界、版本优先级、里程碑
- 产出：`MVP 范围 + 版本规划`

8. `技术方案`
- 使用 `bmad-agent-architect`
- 进入条件：MVP 已明确
- 产出：`技术架构 + 模块拆分 + 实现策略`

9. `实施准备`
- 使用 `bmad-check-implementation-readiness`
- 目标：检查 Brief、MVP、架构是否足够完整，避免带着模糊进入开发
- 产出：`ready / not ready` 判断和缺口清单

10. `需求拆解`
- 使用 `bmad-create-epics-and-stories`、`bmad-create-story`、`bmad-dev-story` 或 `bmad-agent-dev`
- 目标：把确认后的产品规划变成可执行开发单元
- 产出：`epics`、`stories`

11. `功能开发`
- 使用 `bmad-dev-story` 或 `bmad-agent-dev`
- 目标：按 story 完成功能开发和必要修复
- 产出：实现结果

12. `自动测试与验收`
- 使用 `bmad-agent-qa`、`bmad-qa-generate-e2e-tests`、`bmad-code-review` 或 `code-review`
- 目标：完成自动化测试、回归验证、验收检查、发布前审查
- 产出：`测试结果`、`验收结论`、`发布前风险`

13. `发布准备与上线`
- 使用 `bmad-agent-pm`、`bmad-agent-dev`、`bmad-agent-architect`
- 目标：确认发布范围、上线步骤、环境检查、回滚方案，并执行上线
- 产出：`发布清单`、`上线步骤`、`回滚预案`、上线结果

14. `上线后跟踪`
- 使用 `bmad-agent-pm`、`bmad-agent-qa`、`bmad-agent-analyst`
- 目标：复盘发布结果、收集问题、判断下一轮迭代
- 产出：`发布复盘`、`后续优化清单`

15. `增长与迭代决策`
- 使用 `bmad-agent-pm`、`bmad-agent-analyst`
- 目标：基于上线后数据决定 `继续放大`、`优化`、`暂停` 或 `转向`
- 产出：`增长判断 + 迭代优先级 + 下轮计划`

## 阶段切换规则
- 当前阶段 `允许继续推进` 时，才进入下一阶段
- 当前阶段 `不允许继续推进` 时，必须先补缺口或回退
- 如果用户的问题横跨多个阶段，优先回答 `更上游、影响更大的阶段`
- 如果用户直接要求下游阶段，但上游条件未满足，要明确说明 `为什么不能直接进入`

## 阶段门禁
满足以下条件前，不要进入下一阶段：

- 未完成 `方向筛选`：不要进入 `问题 / 需求验证`
- 未完成 `问题 / 需求验证`：不要进入 `Product Brief`
- 未完成 `中国大陆 + 海外竞品分析`：不要做 `立项决策`
- 若 `中国大陆市场` 或 `海外市场` 任意一侧已经足以否定方向：不要继续停留在 `市场与竞品` 的后续判断，必须先回退到 `问题 / 需求验证`
- 未完成 `差异化切口判断`：不要确认 `值得继续`
- 未完成 `go / no-go`：不要进入 `Product Brief`
- 未完成 `MVP 边界`：不要做 `技术架构`
- 未通过 `implementation readiness`：不要开始 `正式开发`
- 未完成 `stories` 拆解：不要做 `大规模并行开发`
- 未完成 `自动测试 / 回归验证`：不要进入 `正式上线`
- 未确认 `发布清单 + 回滚预案`：不要执行 `线上发布`
- 未完成 `上线后跟踪`：不要直接给出 `增长结论`

## 自动回退规则
当用户在某个阶段提出的新信息、质疑或反例，导致当前阶段结论不再成立时，必须自动回退到上一个合适阶段，而不是继续往下推进。

### 何时必须回退
- 用户否定了 `目标用户`、`核心痛点`、`付费意愿`、`市场空间`、`差异化`、`MVP 边界`、`技术可行性`、`测试结果` 或 `发布条件`
- 发现关键假设其实没有被验证，或之前判断依据明显不足
- 新竞品、新限制、新反馈使当前结论不再可靠
- 在 `市场与竞品` 阶段，若 `中国大陆市场` 或 `海外市场` 任意一侧已经得出否定性结论，导致该方向无法继续
- 开发、测试、发布阶段暴露的问题，已经影响上游产品或需求判断

### 回退原则
- 回退到 `最近一个能重新回答该问题的阶段`
- 不要一次跳回过头；优先回到最小必要阶段
- 回退后先重新产出该阶段结论，再决定是否重新进入后续阶段
- 如果回退会使后续产物失效，要明确标记这些产物 `暂时失效`

### 默认回退映射
- 质疑 `方向值不值得做` -> 回退到 `方向筛选`
- 质疑 `用户是不是真的痛 / 会不会付钱` -> 回退到 `问题 / 需求验证`
- 质疑 `市场是否拥挤 / 有没有竞品` -> 回退到 `市场与竞品`
- `市场与竞品` 阶段中，若 `中国大陆市场` 或 `海外市场` 任意一侧已足以否定方向 -> 回退到 `问题 / 需求验证`
- 质疑 `目标用户 / 价值主张 / 购买触发点` -> 回退到 `问题定义与价值主张`
- 质疑 `是否值得继续立项` -> 回退到 `立项决策（go / no-go）`
- 质疑 `MVP 范围 / 优先级` -> 回退到 `路线图与 MVP`
- 质疑 `技术实现方式 / 架构边界` -> 回退到 `技术方案`
- 质疑 `需求是否足够明确可开发` -> 回退到 `实施准备`
- 开发中发现 story 拆解不合理 -> 回退到 `需求拆解`
- 测试中发现功能不符合需求 -> 回退到 `功能开发`，必要时继续回退到 `路线图与 MVP`
- 发布前发现上线条件不满足 -> 回退到 `自动测试与验收` 或 `发布准备与上线`
- 上线后发现用户不用 / 不买 / 指标差 -> 回退到 `问题 / 需求验证`、`市场与竞品` 或 `立项决策（go / no-go）`

## 执行工作流
除非用户明确要求更窄的范围，否则按以下顺序：
1. 识别任务类型
2. 仅收集最少必要上下文
3. 尽早澄清模糊点
4. 若某个方向已进入 `可立项候选`，先做 `中国大陆市场竞品分析 + 海外市场竞品分析`
5. 先判断 `是否有足够差异化切口`，再决定是否进入 `Product Brief / MVP / 页面流程`
6. 先给结论，再给依据、下一步角色建议与是否应写入项目文档
7. 在适当时沉淀重要决策，优先更新已有主题文档，避免拆成大量小文件
